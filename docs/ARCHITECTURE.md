# Архитектура релиза 0.2

Browser → Express HTTP / WebSocket → SQLite + filesystem (один persistent Docker volume).

React 19 + TypeScript + Vite загружают редактор отдельным чанком. Fabric.js отвечает за объекты и рендеринг. Слой приложения управляет страницами, свойствами и сериализацией. Yjs объединяет совместные изменения и обеспечивает локальный UndoManager. PDF/PNG/JPG генерируются браузером; Sharp на сервере проверяет, ограничивает, поворачивает и перекодирует загрузки в PNG.

## Документ и совместная работа

`projects.document = {pages:[{id,canvas:FabricJSON}]}` остаётся совместимым с первым релизом. Объекты имеют постоянные id; копирование выдаёт новые id, в том числе вложенным объектам группы. Старые документы получают id при открытии совместной сессии. Размер проекта общий для страниц, изображения встроены в документ.

В Y.Doc название хранится в `project`, страницы — в Y.Map `pages`. Каждая страница содержит метаданные canvas и Y.Map объектов. Свойства объекта хранятся независимо, поэтому изменение координат одним редактором не отменяет изменение цвета другим. Порядок задают позиция и стабильный id для разрешения совпадений. Конкурентное изменение одного свойства разрешается детерминированно по правилам Yjs. Текст — строковое свойство целого блока, не Y.Text: посимвольное совместное редактирование не реализовано.

Клиент отправляет только разницу относительно действительно показанного состояния. Неизвестные локальной вкладке чужие объекты/поля не перезаписываются. Во время перетаскивания или ввода текста отображение входящих изменений откладывается до завершения действия, после чего берётся актуальный объединённый Y.Doc. UndoManager отслеживает только локальные транзакции; чужие действия не входят в Undo.

Сервер сначала применяет update к отдельной копии состояния, проверяет документ и лимиты, затем в одной SQLite-транзакции сохраняет JSON, полное состояние Yjs и revision. Только после COMMIT отправляется ack. Непринятое обновление не изменяет действующий документ. Таблица `collaboration` создаётся идемпотентно без удаления старых данных. В ней сохраняется epoch сессии, поэтому обычный рестарт и повторное подключение не сбрасывают историю CRDT.

Контрольная версия создаётся перед первым принятым изменением комнаты и затем не чаще раза в 30 секунд при изменении содержимого. Хранятся последние 30 версий. REST-обновления сохраняют проверку revision, а активные комнаты получают их через Yjs. Метаданные без изменения документа не сбрасывают epoch. Внешняя замена документа при неактивной комнате может создать новый epoch: старая вкладка потребует экспорт JSON и перезагрузку, чтобы не перезаписать новый документ.

## Переподключение

WebSocket автоматически переподключается с задержкой 0,5–10 секунд. Клиент объединяет состояние сервера с локальным Y.Doc и отправляет недостающую разницу. Локальные неподтверждённые данные сохраняются **только в памяти открытой вкладки**. Beforeunload предупреждает о них; закрытие вкладки или процесса до ack может потерять правки. Постоянное офлайн-хранилище ещё не реализовано.

## Авторизация

Пароль: scrypt с индивидуальной случайной солью. Сессия действует 7 дней, в БД хранится SHA-256 токена. Cookie HttpOnly/SameSite=Lax; Secure включается через COOKIE_SECURE. HTTP-изменения проверяют Origin при наличии. WebSocket требует совпадающий Origin, действующую cookie и доступ к конкретному проекту при handshake.

Каждый WebSocket-пакет заново проверяет сессию и роль. Reader получает документ, но не может отправлять изменения. Доступ отзывается через закрытие соединений; смена роли доставляется в интерфейс. Выход из аккаунта закрывает его открытые соединения. Каждые 15 секунд heartbeat дополнительно проверяет сессии и удаляет зависшие соединения. Присутствие формируется сервером из аутентифицированной личности; клиент не может подставить чужое имя. Курсоры и присутствие не сохраняются.

Лимиты: HTTP body 20 МБ, JSON-документ 15 МБ, upload 10 МБ / 25 Мп, 100 страниц, 2000 объектов на страницу, состояние Yjs 20 МБ, 500 WebSocket-соединений на процесс, 20 на пользователя, 100 сообщений/сек на соединение. Slow clients отключаются. Глобальных квот хранения, промышленной DDoS-защиты и распределённых лимитов нет.

## Эксплуатация

Multi-stage Dockerfile: npm ci по lockfile с сохранением TLS/integrity, tsc/Vite, offline prune dev dependencies; runtime Node 24 под непривилегированным пользователем, persistent volume, healthcheck. Нужен reverse proxy с поддержкой WebSocket Upgrade и сохранением Host/Origin. Схема предполагает **один backend-процесс**: Redis/pubsub для нескольких процессов не реализован. Yjs tombstones пока не компактизируются; при достижении лимита состояния следует экспортировать JSON и создать новый проект.

Схема подходит для пилота, но не заменяет PostgreSQL/Redis/S3/worker архитектуру полного ТЗ. Перед production нужны TLS, мониторинг, квоты, проверенные бэкапы и восстановление, аудит безопасности и нагрузочные испытания.
