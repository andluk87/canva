# Аккаунт и безопасность

В разделе **Настройки** доступны имя профиля, смена пароля, активные сеансы и настоящая двухфакторная защита TOTP. Внешние сервисы и ключи провайдеров не нужны.

## Поведение

- Имя длиной 1–100 символов сохраняется в аккаунте. Email остаётся адресом входа и приглашений; неподтверждённая смена email не предусмотрена.
- Для смены пароля нужен текущий пароль. Новый пароль: 10–256 символов, отличается от старого. Схема хранения совместима с существующей: случайная соль и scrypt. После смены завершаются все другие сеансы этого пользователя; текущий сеанс и сеансы других пользователей сохраняются.
- Список устройств показывает текущий сеанс, время входа, срок действия и описание браузера. Для старых сеансов время входа может отсутствовать. Описание устройства основано на User-Agent, который может быть изменён клиентом; это ориентир, а не подтверждение личности устройства.
- Можно отозвать отдельный другой сеанс либо выйти на всех устройствах. Отозванные cookie перестают работать; открытые WebSocket-соединения проверяются и закрываются. Публичный ID сеанса — HMAC, он отличается от хранимого хеша и не является cookie для входа.

## Двухфакторная защита

1. Введите текущий пароль в блоке защиты и нажмите «Настроить защиту».
2. Добавьте показанный ключ вручную в приложение-аутентификатор с типом «По времени», либо откройте ссылку `otpauth://` в совместимом приложении. Поддерживается стандарт RFC 6238: SHA-1, 6 цифр, период 30 секунд.
3. Введите код приложения. Настройка живёт 10 минут; до подтверждения защита не включается.
4. Скачайте 10 резервных кодов и сохраните отдельно от пароля. Коды показываются один раз и хранятся только в виде хешей. Каждый работает один раз. При подтверждении настройки другие сеансы завершаются.
5. При входе введите пароль и код аутентификатора либо резервный код. Допускается отклонение часов на один период; уже использованный TOTP-период нельзя использовать повторно. При включённой защите отсутствие кода не создаёт сеанс.

Для отключения защиты или обновления резервных кодов требуются текущий пароль и действующий одноразовый/резервный код. Обновление делает старые резервные коды недействительными.

Секреты TOTP в SQLite зашифрованы AES-256-GCM. Ключ создаётся в `DATA_DIR/account-security.key` с правами `0600` и сохраняется в том же Docker volume, что база. При резервном копировании сохраняйте базу и этот файл вместе. Удаление ключа при сохранении базы делает существующие TOTP-секреты недоступными; не удаляйте и не регенерируйте его при обновлении. Доступ к серверному volume означает доступ к данным приложения; шифрование не заменяет защиту хоста и резервных копий. Секреты и резервные коды не отправляются в логи, API настройки возвращают `Cache-Control: no-store`.

В этой версии нет восстановления пароля по email, OAuth, подтверждения смены email и административного обхода двухфакторной защиты. При потере приложения используйте сохранённый резервный код.

## API

Все маршруты, кроме существующего `/api/auth/login`, требуют аутентификацию cookie.

| Метод и путь | Данные/результат |
| --- | --- |
| `PATCH /api/account/profile` | `{name}` → `{user}` |
| `POST /api/account/password` | `{currentPassword,newPassword}` → `{ok,revoked}` |
| `GET /api/account/sessions` | `{sessions:[{id,current,created,expires,userAgent}]}` |
| `DELETE /api/account/sessions/:id` | Отзыв другого своего сеанса; текущий возвращает 409 |
| `POST /api/account/logout-all` | Отзыв всех своих сеансов и очистка cookie |
| `GET /api/account/security` | `{twoFactorEnabled,enabledAt,recoveryCodesRemaining}` |
| `POST /api/account/2fa/setup` | `{currentPassword}` → `{secret,otpauthUri,expires}` |
| `POST /api/account/2fa/confirm` | `{currentPassword,code}` → `{ok,recoveryCodes}` |
| `POST /api/account/2fa/recovery` | `{currentPassword,code}` → `{recoveryCodes}` |
| `POST /api/account/2fa/disable` | `{currentPassword,code}` → `{ok}` |
| `POST /api/auth/login` | `{email,password,twoFactorCode?}`; при необходимости второго фактора — 401 и `requiresTwoFactor:true` |

Изменения схемы добавляют `sessions.created`, `sessions.user_agent` и таблицу `account_security`, не удаляя существующие данные. При новых входах SQL INSERT должен явно указывать список столбцов.

## Проверка

`node --test tests/accounts.test.mjs` проверяет валидацию профиля, права на сеансы, отсутствие возможности входа через ID сеанса, смену пароля и изоляцию пользователей, отзыв сеансов, RFC-векторы TOTP, шифрование, истечение настройки, обязательность второго фактора, повторное использование кодов, ротацию резервных кодов и отключение защиты.

`npx playwright test tests/e2e/accounts.spec.ts` выполняет реальные браузерные сценарии профиля/пароля и настройки TOTP/входа/скачивания резервных кодов.
